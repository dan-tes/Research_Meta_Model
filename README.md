# Ранняя остановка обучения: прогноз «сколько улучшения ещё осталось»

Исследование: можно ли из первых эпох кривой `val_loss` предсказать, сколько
относительного улучшения ещё доступно, и на этом основании останавливать обучение
раньше классического `patience` — разменивая эпохи на небольшую и предсказуемую
потерю качества.

**Цель — не обыграть `SimpleEarlyStopping(patience=5)` по итоговой метрике.** Он
и не должен проигрывать: `patience=5` почти всегда доводит до oracle. Задача
прогнозиста — экономить эпохи так, чтобы просадка качества оставалась малой, а
редкие «плохие» остановки концентрировались на шумных и коротких кривых.

Ветка `gbm-forecaster-done-right` — **вариант C**: табличный GBM-прогнозист,
переделанный после того, как первая табличная мета-модель систематически ошибалась
на свежих кривых (см. [«История» ниже](#история-почему-вариант-c)).

Подробный справочник по коду, параметрам и графикам — [docs/early_stopping.md](docs/early_stopping.md).

---

## Идея

«Умная» остановка смотрит на префикс кривой `val_loss`, оценивает **ещё доступное
относительное улучшение** `rel_gain` за горизонт из `H` эпох и останавливает
обучение, когда

```
rel_gain < epoch_penalty · H
```

`epoch_penalty` — минимальное относительное улучшение `val_loss` (к текущему
лучшему), оправдывающее одну лишнюю эпоху. Больше `epoch_penalty` → раньше стоп.
Компромисс «скорость ↔ качество» задаётся этим числом; у каждой стратегии оно
своё (`PENALTY_BY_STRAT`, см. [§3](#3-штраф-калибруется-отдельно-для-каждой-стратегии)),
`EPOCH_PENALTY` в [pytorch_version.py](pytorch_version.py) — общий дефолт `0.006`.

Отличаются стратегии тем, **как** они оценивают `rel_gain` (и на каком горизонте
`H`: `smart_meta` — 10, `smart_trend` / `param` — 5).

| стратегия | оценка `rel_gain` | файл |
|---|---|---|
| `SimpleEarlyStopping` | нет прогноза: классический `patience` (N эпох без улучшения `val_loss`) | [pytorch_version.py](pytorch_version.py) |
| `smart_trend` *(дефолт «умной»)* | линейная экстраполяция `val_loss` по окну из 6 эпох | [pytorch_version.py](pytorch_version.py) `_forecast_trend` |
| `smart_meta` *(вариант C)* | табличный GBM предсказывает `rel_gain` **напрямую** | [meta_forecaster.py](meta_forecaster.py) |
| `param` | фит экспоненты `a·e^(−bt)+c`, прогноз с неё | [pytorch_version.py](pytorch_version.py) `ParametricEarlyStopping` |

`smart_meta` включается только при наличии обученного `models/meta_forecaster.pkl`;
иначе — тихий откат на `smart_trend`.

## Вариант C: табличный GBM-прогнозист

[meta_forecaster.py](meta_forecaster.py). Архитектура — градиентный бустинг
(`sklearn.HistGradientBoostingRegressor`) над таблицей из ~21 безразмерного
признака префикса кривой (наклоны на разных окнах, кривизна, улучшение за
последние 3/5 эпох, эпох с последнего минимума, смены знака дельты, …). Кривая
нормируется делением на `val_loss[0]`, поэтому признаки одинаковы для
классификации (CE) и регрессии (MSE).

Две головы, обученные на одних и тех же признаках:

* **`relgain`** — ещё доступное относительное улучшение `val_loss` за следующие
  `HORIZON = 10` эпох. Именно это использует `smart_meta` для решения об остановке.
* **`plateau`** — через сколько эпох `best-so-far` выйдет на ε-окрестность
  итогового минимума (диагностический таргет, в решении не участвует).

Честная оценка при обучении — `GroupKFold` по задаче: окна одной задачи не текут
между train и val.

Полное описание модели (данные, признаки, таргеты, инференс, метрики) —
[docs/variant_c_forecaster.md](docs/variant_c_forecaster.md).

### История: почему «вариант C»

Первый табличный прогнозист (`_forecast_meta`, удалён) был обучен на
`data/final.csv` — почти сошедшихся MNIST-Keras кривых — и предсказывал
**одношаговую** дельту loss, которую затем авторегрессионно раскатывал на
несколько эпох. На свежих, быстро падающих кривых он систематически выдавал
«изменение ≈ 0» → «умная» остановка всегда срабатывала на полу `min_epochs + patience`.

Вариант C чинит ровно две вещи, оставляя архитектуру (бустинг над таблицей):

1. **Данные** — кривые из того же PyTorch-пайплайна, что и весь бенчмарк
   ([gen_curves.py](gen_curves.py)), а не из постороннего `final.csv`.
2. **Таргет** — прямой прогноз `relgain` за горизонт вместо одношаговой дельты
   с авторегрессией.

## Данные и held-out дисциплина

[gen_curves.py](gen_curves.py) обучает MLP на сетке гиперпараметров
(ширина/глубина/lr/wd/dropout/размер выборки/label-noise) и пишет `val_loss` и
`val_metric` по эпохам. **8 train-задач** (MNIST, FashionMNIST, sklearn digits /
breast-cancer, diabetes, два синтетических регрессора, student-CGPA) →
`data/curves_train.jsonl` (~800 кривых). **3 held-out задачи** (CIFAR-10 как
MLP на flatten, California housing, Wine quality) → `data/curves_eval.jsonl`.

Train- и eval-задачи **не пересекаются**. Прогнозист обучается только на
`curves_train.jsonl`, оценивается только на `curves_eval.jsonl`.

## Результаты

### 1. Прогнозист vs линейный тренд (held-out задачи)

`python meta_forecaster.py eval` — 39 900 окон из held-out кривых:

| таргет `relgain` | MAE | R² |
|---|---|---|
| **GBM (вариант C)** | **0.0074** | **+0.46** |
| линейный тренд (baseline) | 0.0241 | −7.8 |

Разбивка по задачам (MAE `relgain`): california 0.015 vs 0.049 · cifar10 0.0037
vs 0.0084 · wine 0.0037 vs 0.015. GBM стабильно точнее линейного тренда в
**3–4×** на данных, которых он не видел.

`results/fig6_calibration.png` — калибровка прогноза на held-out окнах (тесно у
нуля, т.е. в зоне, где принимается решение об остановке) и разбор, где именно
промахивается линейный тренд: на гладко-падающих кривых он экстраполирует
наклон слишком далеко, GBM держит ошибку ровной.

Точность бинарного решения «продолжать?» (`relgain ≥ epoch_penalty·5`):

| penalty | budget | GBM acc | trend acc | доля «да» |
|---|---|---|---|---|
| 0.006 | 0.030 | 0.939 | 0.902 | 0.106 |
| 0.012 | 0.060 | 0.967 | 0.932 | 0.051 |
| 0.030 | 0.150 | 0.989 | 0.960 | 0.013 |

> Классы сильно несбалансированы (при `penalty=0.03` «продолжать» истинно лишь в
> 1.3 % окон), поэтому accuracy здесь во многом — точность класса «стоп». Честнее
> смотреть на MAE регрессии и на бенчмарк стратегий ниже.

### 2. Линейный тренд vs экспоненциальный фит как прогнозист кривой

`results/fig4_forecast.png` — rel-MAE многошагового прогноза `val_loss` на
held-out кривых. Линейный тренд заметно точнее фита экспоненты на всех
горизонтах: rel-MAE тренда `0.04 → 0.10` (h=1…10), у `param` `0.17 → 0.21` —
хуже в **3–5×**. Поэтому `param` при дефолтном штрафе стопает раньше и теряет
больше качества.

### 3. Штраф калибруется отдельно для каждой стратегии

Один и тот же `EPOCH_PENALTY` означает для прогнозистов **разное**: бюджет =
`penalty · horizon`, а `horizon` равен `10` у `smart_meta` и `5` у
`smart_trend` / `param`. Плюс линейный тренд оптимистично смещён (тянет недавний
наклон дальше, чем кривая реально идёт) и потому «тормозит» позже честного GBM
при том же пороге. Поэтому у каждой стратегии свой штраф — `PENALTY_BY_STRAT` в
[eval_early_stopping.py](eval_early_stopping.py), откалиброван по свипу
(`holdout_sweep.csv`, fig3) так, чтобы держать gap до oracle на held-out ~2–3 п.п.
при максимальной экономии эпох:

| стратегия | штраф (общий) | классификация | регрессия | заметка |
|---|---|---|---|---|
| `smart_trend` | **0.006** | 0.006 | 0.010 | рабочая лошадка, тюнится плавно на всём |
| `smart_meta` (вариант C) | **0.003** | 0.003 | 0.006 | ≈ ½ штрафа `smart_trend` — честный прогноз + горизонт 10 |
| `param` | **0.010** | *не тюнится¹* | 0.012 | exp-fit управляем только на гладкой регрессии |

¹ на классификации `param` стопает на ~15–19 эпох при любом штрафе (форма
CE/accuracy-кривой не описывается экспонентой) — использовать не рекомендуется.
На **CIFAR-MLP** ни один штраф `> 0.001` не даёт gap `< 2` п.п. ни для одной
стратегии: кривая улучшается слишком долго. Это принятый режим («худшие
остановки на нетипичных кривых»).

### 4. Итог бенчмарка (`results/fig7_headline.png`, fig1–2)

При калиброванных штрафах, усреднено по всем (задача, размер, seed):

| стратегия | эпох (доля от `early`) | потеря качества до oracle |
|---|---|---|
| `early` | 1.00 | 1.7 % |
| `smart_meta` (вариант C) | 0.62 | 5.3 % |
| `smart_trend` | 0.64 | 5.7 % |
| `param` | 0.59 | 7.7 % |

По задачам (`smart_meta` vs `smart_trend`): MNIST 0.73 / 0.6 % vs 0.78 / 0.6 % ·
Wine 0.67 / 4.5 % vs 0.69 / 4.5 % · CIFAR 0.42 / 12 % vs 0.43 / 13 %.

**Вывод.** После калибровки штрафа `smart_meta` и `smart_trend` **на равных** —
GBM больше не проигрывает (при общем штрафе `0.006` он казался хуже только из-за
горизонта 10). `param` отстаёт. Но выиграть у `patience = 5` по итоговой метрике
не может ни одна прогнозная стратегия — это [и не
цель](#ранняя-остановка-обучения-прогноз-сколько-улучшения-ещё-осталось): все
разменивают ~35–40 % эпох на потерю качества от ~0.6 % на знакомых кривых
(MNIST) до ~12–13 % на CIFAR-MLP.

Как *прогнозист* `relgain` вариант C по-прежнему в 3–4× точнее и линейного
тренда, и экспоненциального фита на held-out (fig6) — просто эта точность
упирается в то, что решение принимается ради `val_metric`, а прогноз строится по
`val_loss`.

### 5. Режимы: мало данных и «резкие» кривые (`analyze_regime.py`, fig8)

Симуляция всех стратегий на held-out кривых без переобучения сетей —
`python analyze_regime.py` → `results/regime.csv`, `fig8_regime.png`. Проверяли
гипотезу «GBM вытягивает качество там, где мало данных / кривая резкая, а
тренд и exp-fit нестабильны».

* **Объём данных.** Все прогнозные стратегии на малых `train_size` теряют
  больше (медианный gap ~2–3× от `early`); с ростом данных gap сжимается.
  `smart_meta` ≈ `smart_trend` на **каждом** размере — отдельного выигрыша GBM
  на малых данных в медиане нет.
* **«Резкие смены» — не там, где кажется.** Кривая с резким скачком `val_loss`
  вверх уже прошла минимум → лучший чекпойнт ранний → остановиться легко, все
  стратегии почти не теряют. Трудные кривые — **гладкие, ещё падающие**, где
  много улучшения осталось впереди (fig8-C: gap растёт монотонно с «недобором»).
* **Кто на самом деле нестабилен — `param` (exp-fit).** На кривых с большим
  недобором его gap ≈ 0.12 против ≈ 0.054 у `smart_meta` и `smart_trend` — вдвое
  хуже; на `california`-800 он подскакивает до ≈ 0.09 (fig8-A). GBM и тренд его
  чисто обыгрывают здесь.
* **GBM vs тренд** в этих режимах — паритет по медиане; на мало-данной регрессии
  (`california`) у GBM ниже разброс результата (предсказуемее), но выборка мала.
* **`early` ближе всех к oracle на 96 % held-out кривых** — по отдельной кривой
  прогноз не окупается почти нигде.

**Итог по гипотезе:** для пары GBM ↔ линейный тренд — **не подтверждается**
(паритет, и оба не бьют `early`). Для пары GBM ↔ exp-fit — **подтверждается**:
`param` и есть та нестабильная стратегия, что разваливается на трудных кривых, а
GBM (как и тренд) там вдвое лучше. Собственное преимущество GBM над трендом — в
дисперсии, не в медиане.

## Пайплайн

```
gen_curves.py               # 1. кривые обучения (train / eval — непересекающиеся задачи)
   ↓  data/curves_{train,eval}.jsonl
meta_forecaster.py train    # 2. обучить табличный GBM-прогнозист (вариант C)
   ↓  models/meta_forecaster.pkl
eval_early_stopping.py       # 3. прогнать стратегии (early / smart_trend / smart_meta / param)
   ↓  results/*.csv, results/example_curves.json
plot_early_stopping.py       # 4. графики
   ↓  results/fig1..5.png
```

```bash
N_PER_TASK=100 python gen_curves.py      # ~20–40 мин на GPU
python meta_forecaster.py                # train + held-out eval, секунды
python eval_early_stopping.py            # ~4 мин на GPU  (--quick для черновика)
python plot_early_stopping.py
```

Для `smart_meta` нужны шаги 1–2 (иначе стратегия тихо откатывается на тренд и не
попадает в бенчмарк). `smart_trend` / `param` работают и без них.

| что | где | сейчас |
|---|---|---|
| агрессивность остановки | `EPOCH_PENALTY` в [pytorch_version.py](pytorch_version.py) (дефолт классов, `test.py`); в бенчмарке — `PENALTY_BY_STRAT` в [eval_early_stopping.py](eval_early_stopping.py) | trend `0.006` · meta `0.003` · param `0.010` |

| кривых на задачу | `N_PER_TASK` (env) в [gen_curves.py](gen_curves.py) | `100` |

## Готчи

* **held-out дисциплина.** `data/curves_eval.jsonl` / `EVAL_TASKS` не должны
  пересекаться с `curves_train.jsonl` / `TRAIN_TASKS` / `final.csv` — иначе оценка
  прогнозиста завышена.
* **CIFAR в бенчмарке — это MLP на `flatten(3072)`**, не CNN. Форма кривых
  реалистична, абсолютная accuracy низкая — это ок, меряем стратегию остановки.
* **`oracle`** в CSV = метрика на лучшем по `val_loss` чекпойнте за полный прогон
  без остановки, а не `max(val_metric)`.
* **`smart_meta` появляется в бенчмарке только при наличии
  `models/meta_forecaster.pkl`** (`eval_early_stopping.py` проверяет `_SMART_HAS_META`).
* Старый `_forecast_meta` (final.csv + одношаговая дельта + авторегрессия) удалён;
  `use_meta=True` без обученного `.pkl` = тихий откат на тренд.
